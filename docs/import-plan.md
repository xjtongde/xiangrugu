# import-plan.md —— usedata → pg32b/xiangrugu 导入方案

> 状态：现行方案｜as_of 2026-10-06

## 1. 目标与边界

唯一输入是 `/mnt/wd61workmetadata/usedata`，目标是 32 主机 `pg32b` 实例中新建的 `xiangrugu` 数据库。现有 `cbdb` 只可观察，不得参与清单生成、字段映射、期望值计算或验收；其删除不属于本方案执行范围，须另获授权。实例中另有旧彩排库 `cbdb_reh`，同样不属于本方案目标或基线，处置待用户另行决定。

本项目只负责忠实搬运与可验证重建，不负责判断、清洗或修正源数据。导入过程不得改源件，也不得接触同机 `pg32` 的数据或配置。

## 2. 完成定义

以下条件同时满足才算完成：

1. `usedata` 的每个文件及容器内成员均有唯一记录和处置；
2. 处置只能是 `IMPORT`、`MIRROR`、`NON_TABULAR` 或 `BLOCKED`，并带理由和证据；
3. 正式验收时 `BLOCKED=0`，不存在 `PARTIAL` 或未登记成员；
4. 所有 `IMPORT` 对象通过结构、数量、值、几何/栅格和溯源验证；
5. 两次全量彩排结果一致，失败后可安全重跑；
6. 正式库可仅凭源件、配置和指定 Git 提交重建；
7. 所有表都有机器可读合格证书，汇总状态为 `CONFORMS`。

## 3. 导入合同

### 3.1 盘点合同

`datamgmt/recon/inventory_members.tsv` 负责成员级枚举；`ledger_final.tsv` 当前只是盘点草案，不是已批准的最终合同。开发前必须处理：

- 跨载体同名数据组的保留策略；
- `v4_chgis_dbase.mdb` 非同字节副本；
- `Thumbs.db` 等非业务成员的处置；
- 当前草案中的目标 schema 与本方案的最终 schema 映射。

草案中的每行最终都须进入 `config/sources.yaml`，或由可追溯规则归入 `MIRROR`/`NON_TABULAR`。禁止靠文件扩展名白名单静默跳过。

### 3.2 目标结构

建议正式库使用四个 schema：

| schema | 内容 |
|---|---|
| `cbdb` | CBDB SQLite 来源对象 |
| `chgis` | CHGIS 空间、属性及配套对象 |
| `harv` | Harvard 其他数据集 |
| `audit` | 导入运行、成员处置、闸门结果和合格证书 |

现有底账把 CBDB 目标写为 `public`，这是旧草案状态；在生成 `sources.yaml` 前必须显式迁移为 `cbdb`，不能由装载器临时猜测。

### 3.3 声明式配置

- `config/roots.yaml`：源根、目标实例和安全边界；
- `config/sources.yaml`：一源对象一条，记录成员链、载体、目标、处置、字段与验证策略；
- `config/decoding.yaml`：文本列级编码、判定依据和不可解码策略；
- `config/g4_assertions.yaml`：已确认源生现象的非阻塞语义哨兵。

配置由盘点证据生成并经人工审阅，运行时不得从旧库反推。

## 4. 实现架构

### 4.1 三条独立路径

```text
源字节 ── 独立读取器 ──> 期望结构和值 ─┐
                                         ├─> verifier ─> audit 证书
源字节 ── importer ──> staging ──> 正式表 ┘
```

装载器与验证器不得共用值解析实现；可以共用稳定的数据结构定义，但不能让同一个解析错误同时制造“结果”和“答案”。验证期望值不得来自 PostgreSQL 导出或装载器中间文件。

### 4.2 载体竖切

先为每类载体打通一个最小但完整的竖切：枚举、解析、装载、验证、故障注入、重跑，再扩展到该载体全量。至少覆盖：

- SQLite；
- Shapefile/DBF/PRJ；
- MapInfo TAB/DAT/MAP/ID；
- XLS/XLSX、CSV/TSV/ODS；
- MDB；
- SQL dump；
- GeoTIFF 及其他需保留的栅格/影像；
- ZIP 及多层容器成员链。

当前代码尚未覆盖上述全部载体，详见 `datamgmt/README.md`；现状不能据此宣称方案已实现。

### 4.3 装载与发布

每个对象先进入唯一运行命名空间下的 staging。验证通过后，在同一数据库事务中完成旧正式对象处理、staging 改名、审计记录和提交；任一步失败必须整体回滚。

现有 `importer/load.py` 的 `DROP` 与 `ALTER ... RENAME` 分两次调用，尚未证明处于同一事务，必须在开发阶段修正并测试后才可用于正式发布。

## 5. 验证闸门

| 闸门 | 必须证明的事实 |
|---|---|
| G0 源完整性 | 校验账、源件存在性、可读取性；运行前后源摘要不变 |
| G1 覆盖 | 全部成员有处置；容器内部表、sheet、图层和伴随文件无遗漏 |
| G2 结构 | schema、表、列、顺序、类型语义、空值规则、CRS/栅格元数据符合合同 |
| G3 数量 | 每个源对象与目标对象的有效记录数按同一口径精确相等 |
| G4 值全等 | 独立读取结果与库值逐行逐列比较；文本比较解码后的码点并保留原始证据 |
| G5 空间/栅格 | 几何类型、坐标、部件、SRID 声明及栅格尺寸、波段、仿射参数等一致 |
| G6 可重复性 | 重跑不产生重复或漂移；两次全量彩排证书一致 |

哈希只能用于定位和加速，不能替代值级验证。抽样只可用于开发反馈，不能用于正式放行。

每表证书至少包含：源成员链与摘要、配置版本、目标名、结构摘要、源/目标计数、值比较结果、空间/栅格结果、运行 ID、Git 提交和最终状态。

## 6. 测试策略

1. 单元测试：各载体读取、编码、标识符、空值、类型和容器展开；
2. 故障注入：故意制造漏行、错码、错列、重复、几何变化、错误处置和中断，证明对应闸门会失败；
3. 载体集成：每类载体完成源到 staging 到验证到回滚/发布；
4. 全库回归：对全部 `sources.yaml` 运行并生成汇总证书；
5. 重入测试：中断后重跑、成功后再跑，结果不重复、不漂移；
6. 两次全量彩排：在相同源和提交下独立重建并比较证书。

`datamgmt/tests/` 当前只有占位文件，没有测试代码；这是开工后的首要缺口之一。

## 7. 环境与安全

使用三个数据库名隔离用途：

- `xiangrugu_sample`：载体竖切和小样测试；
- `xiangrugu_rehearsal`：全量彩排，可反复重建；
- `xiangrugu`：最终正式库。

三者都位于 `pg32b`，但创建、删除或重建任何数据库都需单独取得用户授权。现有 `cbdb`、`cbdb_reh` 不复用为任一环境。

`pg32b` 与 `pg32` 同宿主。`nice`/`ionice` 只能降低调度优先级，不能防止内存、磁盘空间、I/O 或连接耗尽。正式执行前必须设置并验证：并发上限、连接上限、批大小、磁盘余量门槛、内存门槛、负载熔断、可观测指标和停止程序；先做 canary，再逐步扩量。

## 8. 实施阶段与出口

| 阶段 | 工作 | 出口条件 |
|---|---|---|
| 0 合同收口 | 复核盘点、裁定冲突、确定 schema 与处置 | 100% 成员有唯一处置；用户批准合同 |
| 1 基础能力 | 完成配置格式、审计模型、独立验证框架和测试骨架 | 配置校验及故障注入测试通过 |
| 2 载体竖切 | 每类载体完成端到端最小闭环 | 每类至少一项通过全部适用闸门 |
| 3 载体全量 | 按载体扩展至全部合同项 | 无未实现载体；无静默跳过 |
| 4 全量彩排 | 重建 `xiangrugu_rehearsal` 两次 | 两次均 `CONFORMS` 且证书一致 |
| 5 正式构建 | 新建并构建 `xiangrugu` | 全部证书通过，交付重建说明 |

阶段不得仅凭“脚本存在”或“命令运行成功”跨越。
