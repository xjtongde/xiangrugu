## §1 标尺与合格的定义

**用户标尺（2026-09-29 原话照录，不改写）**：

> 「**源数据的错误与对，不是我们来判断的。我们的依据就是源数据。如果我们无错的把源数据导入了。那我们的工作就没有问题。我们的核心工作就是无错的把源数据，导入到pg32b数据库。**」

配套纪律＝`rules.md` **R-07**（源数据只记不改：源数据有问题只记录、不修改，除非用户逐案指定）。

**"无错"的可判定定义（本方案一切验收以此为准）**：

> 对**每一个源件 → 每一张表 → 每一列 → 每一行 → 每一个值**：
> **库内值 ＝ 源件字节按《§5.4 列级解码判定表》读出的值。**
> 差异必须为 **0**；或逐条挂编号解释，且解释**只允许两类**（§6.4 白名单）。

**由此推出的三条否定式判据**（旧方案的验收全部栽在这里）：

- 行数相等 **不等于** 无误（P-01／P-05）；
- 表指纹（哈希聚合）相等 **不等于** 无误（P-02）；
- 执行记录的叙事账 **不能** 作为合格证明（P-10）。

**责任边界**：源数据自身的可疑处（讹字、离群坐标、占位符、纪年越界、同名同生年、无外键）**不是我们的错、也不由我们修**——只登记（§8）。我们的合格线只有一条：**搬运过程零损伤、零添加、零改写**。

datamgmt/                     ← 一律入 git（不再放 ops/；此为 P-16 之戒）
├── README.md                 模块定位、五条纪律、阶段表（唯一入口）        【已建】
├── PITFALLS.md               ★防坑条目录 P-01…P-25（本方案各规则之依据）  【已建，自 docs/ 迁入】

│   ├── sources.yaml          源清单：一源一条，"库应该长什么样"的唯一记载（§5.1）【阶段二，候口令】

│   ├── shp.py                SHP 几何直解（顶点 double 原值、形状类型、bbox）

**三件核心东西**＝`config/sources.yaml`（声明"库该长什么样"）＋`importer/load.py`（照声明装）＋`verifier/verify.py`（用 `truth/` 独立读源件字节来验）。**`decode.py` 之列级解码判定，由 `importer/` 与 `verifier/` 各自独立实现一遍**（读同一份 `config/decoding.yaml`，实现不同而结果同才算真验——§6.1 独立性铁律）。

### 4.2 数据流

```text
NAS 权威源 usedata/            源件字节
      │                        （sha256 对 SHA256SUMS-b2，现况 173/173 OK）
      ├──────────────► truth/  独立直读 → 真值（件数/行数/列集/类型/CRS/逐值）
      │                                  │
      └──► load.py（GDAL/COPY 装载）      │
                 │                        │
             staging 表 ──► 闸1..闸3 ◄─────┘   （比对，不过即停）
                 │
             原子换名 → 保真层 schema
                 │
             闸4（语义哨兵）＋ 闸0/闸5
                 │
        recon.tsv ＋ cert/<表>.json（合格证书）
```

**关键性质**：真值这条线**从不经过装载器**；装载器**从不自证**。

### 4.3 库内分层（只有一层是保真层）

| schema | 内容 | 允许的操作 |
|---|---|---|
| `public`／`chgis`／`harv` | **保真层**：与源件逐值全等 | 只允许 `CREATE`／`DROP`＋重装；**永不 `UPDATE`／`DELETE`**（H-3） |
| `ogr_system_tables` | 装载器副产物（如 `metadata`） | 原样保留（它也是"源件之外我方引入之物"，须在证书里单列声明） |
| （不设 `clean` 层） | 清洗／校勘／投影变换**不属核心工作** | 若用户指定要做，另立派生层文档与账，且依 R-07 逐案指定；**不得混入保真层** |

### 5.2 装载分腿（按载体，不按"批次"）

| 腿 | 载体 | 源件规模 | 装载法 | 该载体的专属坑（→ `datamgmt/PITFALLS.md`） |
|---|---|---|---|---|
| **A** | sqlite（CBDB 78 表） | 1 件 586,485,760 B | python `sqlite3` 直读 → `\copy FROM STDIN` | 类型亲和性、BLOB→bytea hex、NULL 语义、标识符大小写 |
| **B** | shapefile＋DBF（CHGIS V2–V6、Hartwell、谭图、明驿路等） | 212 档案（含 zip 套 zip） | `ogr2ogr` **但一切参数显式**；几何**不投影** | LDID 猜编码、混合编码、`-append` 丢列、双重后缀、`.prj` 被"实证"推翻 |
| **C** | xls／xlsx（八表＋专题） | 数十件 | **不用 GDAL 读表**（`.xls` 无表头开选项）→ 直读单元格后 `\copy` | 表头当数据、版权前言、67 个 `fieldN` 伪列 |

### 5.3 类型映射（逐类显式，不用工具默认）

| 源 | 映射 | 备注 |
|---|---|---|
| DBF `C(n)` | `text`（**不设长度上限**） | 列宽截断系源件固有（旧方案 §10 已认定"原样保真不修"；原件已删，见 `git show 75ecd77:docs/cbdb-load.md`）→ 属 §6.4 白名单第②类 |
| DBF `N(w,0)` | `bigint`（超范围者 `numeric`） | 以**源件声明宽度**判，不以数据判 |
| DBF `N(w,d>0)` | `numeric(w,d)` | 禁 `float`（避免十进制→二进制误差，破坏值级全等） |
| DBF `D` | `text` 原样（`YYYYMMDD`） | 不转 `date`：源件有空值/零值形态，转换即改写 |

| sqlite `INTEGER` | `bigint` | 旧方案已定，沿用 |
| sqlite `REAL` | `double precision` | 须在证书声明"浮点原样搬，不做十进制化" |
| sqlite `BLOB` | `bytea`（hex 通道） | 沿用旧方案 §4.2 |
| sqlite `TEXT` | `text` | UTF-8 无歧义 |
| xls/xlsx 单元格 | 按 `sources.yaml` 逐列声明 | **绝不让工具猜** |
| 几何 | `geometry(Geometry,<.prj 之 SRID>)` | **禁止 4326 归一**（H-2）；若源件无 `.prj` → 记 `srid: 0` 并登记为"源件未声明"，**不得推断** |
| 栅格 | `raster` | 像素类型照源；分块参数入证书 |

### 5.4 列级解码判定表（本方案最贵、最值钱的资产）

**问题**：DBF 存的是字节，同一个文件内**不同列可能是不同编码**（实证：`v5_gns_anhui_gbk.dbf` 之 `NAME`/`NM_ASCII`/`SORT_NAME`/`PREF_PY` 系单字节 latin1/cp1252——威妥玛拼音 `ü` 存作裸字节 `0xFC`；而 `CNTY_CH` 系真 GBK）。

**判定表结构**（落 `datamgmt/config/decoding.yaml`（阶段二建，**现未建**），每条须带依据）：

```yaml
- source: v5_gns_*_gbk.dbf        # 或按 DOI 目录/表族归并
  columns:
    NAME:      {encoding: cp1252, evidence: "源字节 48 73 FC 61 6E = Hsüan；0xFC 系 cp1252 ü，非 GBK 前导"}
    NM_ASCII:  {encoding: cp1252, evidence: "同上，130,665/130,665 逐行全等验证过"}
    SORT_NAME: {encoding: cp1252, evidence: "同上"}
    PREF_PY:   {encoding: cp1252, evidence: "同上；1 行含 î"}
    CNTY_CH:   {encoding: GBK,    evidence: "4,099 记录全含高位字节，GBK 解码得汉字"}
  default: {encoding: GBK, evidence: "文件级 LDID 声明＝GBK；仅上列例外"}
```

**判定方法（不许猜）**：① 读 DBF 头 LDID 作为**文件级默认**；② 对每一含高位字节的列，取全部相异字节序列，分别按候选编码解码，**只有全量可解且无替换字符者入选**；③ 有歧义者（如孤立 `0xFC`）→ 用**同表其他列/官方数据字典/发布方 README** 交叉定谳；④ 仍不能定 → **登记为未定，该列不装**（宁可缺，不可错），并在证书里显式声明缺列。

**现状**：此表**不存在**（只有 B-11 对 `v4_gns` 一个表的结论）。它是 §10 阶段二的主要人力所在。

### 5.5 装载流程（幂等）

```text
每源：
  1. 闸0 源件完整性（sha256/件数/成员链/.prj 可读）        → 不过即停
  2. truth/ 独立读源，现算真值（行数/列集/类型/CRS）        → 落 recon
  3. DROP TABLE IF EXISTS <schema>.<table>__stg
  4. 装载入 staging（参数全显式，禁默认）
  5. 闸1 结构 ＋ 闸2 计数 ＋ 闸3 值级（staging vs 真值）     → 不过即停，staging 保留供查
  6. 原子换名：__stg → 正表（同事务内 DROP 旧正表 + RENAME）
  7. 写 recon（upsert 带唯一键）＋ 出证书 cert/<表>.json
全库毕：
  8. 建索引（含 GiST）＋ ANALYZE（PG 官方 §14.4 第 3/8 条）
  9. 闸4 语义哨兵（全库）＋ 闸5 换版差分（若有旧版）
 10. 出《全库合格证书》
```

**幂等性判据**：同一 `sources.yaml` ＋ 同一源件，**任意次数重跑必得逐值相同之库**（含行序无关的值集合相同）。这是"可重建"的定义。

**压力防护（沿用旧方案已验证有效者）**：`nice -n 19 ionice -c3`；loadavg<4.0 门禁（30s 轮询，超时退出）；顺序单流零并行；会话级 `maintenance_work_mem=256MB`（仅索引段）；`max_wal_size` 临时 4GB、毕即 `RESET`（PG 官方第 6 条）；**不采纳** `wal_level=minimal`（须重启＋废基础备份，旧方案有据不采纳，沿用）。pg32b 与生产 pg32 共实例，canary 查询计时须纳入门禁。

## §6 验证卷（六道闸）

### 6.1 独立性铁律（违反任一条，验证即无效）

1. **验证器与装载器零共用代码**（`verify.py` 不得 import `load.py`；`decode.py` 的判定规则由两侧**各自独立实现一遍**，实现不同而结果同，才算真验）；
2. **期望值绝不来自被验收者**（不许 `ok = (cum == 装载器数出来的值)`）；
3. **验收不用 GDAL**——装载可以用，验收必须直读源件字节（`truth/`）；
4. 每道闸输出**机器可读**结果（JSON）＋ 落 recon；
5. 闸不过 → **停**，不"尽力而为"、不"先装完再说"。

### 6.2 六道闸

| 闸 | 判据 | 通过条件 | 治哪个坑 |
|---|---|---|---|
| **闸0 源件完整性** | sha256 对 `SHA256SUMS-b2`；件数；成员链存在；`.prj`/DBF 头可读 | 全数相符 | 源件被动过／搬错／路径腐化（P-13） |
| **闸1 结构（形状哨兵）** | 库内列集 **＝＝** 源字段集（**差集为空**）；无 `^field[0-9]+$` 列名；逐列类型/宽度符合源件声明；几何 SRID **＝＝** `.prj` 声明；栅格像素类型/nodata 符合源件 | 差集 ＝ ∅ 且无伪列且 SRID 相符 | B-10（29 省前缀列静默丢弃）、B-06（114 个 `fieldN`）、**v5_gns SRID 4326 ≠ `.prj`** |
| **闸2 计数** | 行数 ＝＝ 源侧现算真值；并表类 ＝＝ 各成员之和；剔除行数 ＝＝ 结构还原声明数 | 逐一相等 | B-05（漏装 4,099 行）、B-06/FIX11（删 14 行无据） |
| **闸3 值级（核心）** | 见 §6.3 | 差异 ＝ **0** 或逐条挂白名单编号 | **B-11（2,288 值丢字，行数与指纹全过）** |
| **闸4 语义哨兵** | 源数据可疑处登记册之**机器可执行版**（§8.2） | 逐条与登记册相符 | 我方悄悄引入了东西／源件换了版本而未察觉 |
| **闸5 换版差分** | 新旧源件 → 表级/行级/值级 diff | 产出报告（不判过/不过） | 盘上已有两个 CBDB 发行版（20250520／20260919），换版是常态 |

### 6.3 闸3 的四种比对法（按表性质选，选法须写入证书）

| 表性质 | 比对法 | 说明 |
|---|---|---|
| **有唯一键**（CBDB 各表主键、`v4_gns` 之 `(ufi,uni)`） | 按键逐行逐列比 | 最强；差异定位到"哪一行哪一列" |
| **无唯一键**（并表类、部分专题表） | ①全列排序后逐行比；或 ②**行哈希多重集差集**（`md5(所有列::text)` 的 `EXCEPT ALL` 双向） | ②代价低、①可定位；**必须二选一并声明**（§12 待裁口径三） |
| **几何** | 顶点 `double` **逐位相等**（因 H-2 不投影，故应精确相同，**无容差**）；辅以形状类型、顶点数、bbox | 若出现容差需求 → 说明有人做了变换 → 直接判不合格 |
| **栅格** | 分块像素值全量比；或统计量（min/max/mean/stddev/nodata 计数）＋**按块抽样像素全比**，抽样覆盖率须声明 | 全量代价高者分级，但**不得含糊写"抽样通过"** |

**分级策略**：曾出过事的源**全量**（`v4_gns`／`v5_gns`、`hartwell_*`、xls/xlsx 八表、CBDB 78 表）；纯数值/栅格源可抽样，**覆盖率与置信度写入证书**。

### 6.4 差异解释白名单（**只两类**，其余一律判不合格）

| 类 | 允许的差异 | 依据形式 |
|---|---|---|
| **① 结构还原** | 表头行、版权前言、非数据 sheet 未入库 | 该行文本 ＝＝ 源件列名集／位于声明的数据起始行之前（H-4，机器可复核） |
| **② 源件固有形态** | `.dbf` 列宽截断、源件本身的空值/零值写法、浮点二进制表示 | 指向源件字节或官方数据字典的具体条文 |

**明确不属白名单**（历史上都被当成"没办法"混过去了）：编码转换丢字、投影变换、类型推断改值、`-append` 丢列、"装载方便"、"GDAL 默认如此"。

### 6.5 合格证书（每表一份 JSON，全库一份汇总）

```json
{
  "table": "chgis.v5_gns",
  "source_key": "/harvard-full/doi_10_7910/DVN/M7WEFY/v5_gns_*_gbk.zip",
  "sha256_verified": "30/30",
  "truth": {"rows": 130665, "cols": 32, "srid_from_prj": "Xian_1980_GK_Zone_19", "computed_at": "…"},
  "gates": {"g0": "PASS", "g1": "PASS", "g2": "PASS", "g3": {"diff": 0, "method": "keyed", "coverage": "full"}, "g4": "PASS"},
  "whitelisted_diffs": [],
  "verdict": "CONFORMS",
  "loaded_at": "…", "verified_at": "…", "toolchain": {"gdal": "3.13.2", "pg": "18.6", "postgis": "3.6.4"}
}
```

**证书是"无误"的唯一合法证明**；无证书的表＝未验收＝不合格。

## §7 测试卷

### 7.1 单元测试（对 `truth/` 与 `decode.py`，不对库）

- **DBF 直解器**：对一个已知源件，断言字段名/类型/宽度/小数位/LDID/记录数与手工解析结果一致；断言原始字节可还原（`decode(encode(x)) == x`）。
- **解码判定**：对 `v5_gns_anhui_gbk.dbf` 断言 `NAME` 按 cp1252 解出 `Hsüan` 系全量可解、无替换字符；断言 `CNTY_CH` 按 GBK 解出汉字。
- **zip 成员枚举**：断言 `v4_gns_guangxi_gbk.zip.zip` 这类双重后缀件**被命中**（P-08 的回归测试）。
- **`.prj` 解析**：断言能取出 `PROJCS` 名与全部 `PARAMETER`。
- **xls/xlsx 首行判据**：断言"首行文本集合 ＝＝ 列名集合"能识别表头行；断言版权前言落在数据起始行之前。

### 7.2 集成测试（单源端到端，在**临时库**上跑，不动生产）

每类载体挑一个最小源件，跑完整 `load.py`＋`verify.py` 流程，断言：证书 `verdict == CONFORMS`；**并做一次"故意注错"演练**（篡改一个字节/删一个成员/改一列编码），断言**对应的闸必须 FAIL**——**闸抓不到的错，等于闸不存在**。这是本方案最重要的一类测试（旧方案从未做过，故 B-05/B-06/B-10/B-11 全部静默通过）。

### 7.3 全库回归（`verify.py --all`）

- 一条命令跑闸0–闸4，产出全库合格证书；
- **必须可对现库跑**（P-2 前置）：这份《逐值差异账》既是现库体检结果，也是新库验收基准；
- 触发条件：源件变动、`sources.yaml` 变动、`decode.py`/`truth/` 变动、库重装、PG/GDAL/PostGIS 版本变动。

### 7.4 重建演练（正式装载前的彩排）

> **靶机改判（2026-09-30 用户令：「你不要再考虑36主机的事了」「你就当36不存在」）**：原以 **pg36** 为彩排靶机之设计**已作废**，该主机按用户令**视为不存在**（`docs/pg36.md` 已删除）。

**彩排靶＝32 主机 `pg32b` 实例上之另一库名**（如 `cbdb_v3`）。磁盘余量已现算核实：`/` 余 **189G**、现库仅 4,771 MB → 装两遍＋索引余量充足。**用新方案从零装一遍全库**，断言：
1. 全库证书 `CONFORMS`；
2. **与现库 `cbdb` 逐值差分**：差异只能出现在已知不合格处（B-11 的 2,288 值、B-15 的 `v5_gns`/`v4_gns` 几何）与白名单；**跨库比对之机制**（`postgres_fdw`／双侧 dump 排序后比）属阶段二实现细节，**候裁**；
3. 幂等：连跑两遍（两库名或两 schema），两遍结果逐值相同；
4. 工时与资源实测（用于排正式窗口）。⚠ **32 系共生产主机**（`pg32` 在跑）→ 实测须同记 loadavg 与 `nice`/`ionice` 条件，否则该数据无参考价值。

**演练通过 ＝ 才允许动正式库名。** 若用户裁「并行装新库、不删旧库」（§12 口径八），则**本次彩排即正式装载**，二者合而为一。

### 7.5 换版测试（闸5）

以盘上两个 CBDB 发行版（`CBDB_bi_20250520_Build20250604` 与 `cbdb_20260919`）为素材，跑一次差分，验证报告能定位到"哪表、哪行、哪列、旧值→新值"。**这是长期能力的验收，不是本轮必须**。

## §14 官方与社区建议摘要（2026-09-30 自旧方案 `cbdb-load.md` §12 抢救收敛；原件已删，全文可 `git show 75ecd77:docs/cbdb-load.md` 取回）

**结论一句话：三层来源，两有一无——而"无"的那层恰恰决定了本方案只能以源件字节为唯一真值。**

### 14.1 数据方（Harvard CBDB／CHGIS）：**对"入 PG"无任何建议**（全文实证）

- HF 数据卡只有下载点与许可（CC BY-NC-SA 4.0），无迁移指引；
- 《CBDB User's Guide》全文已抓并检索： Fuller 修订版 **153 页**（harvard 直连 403＝服务器端反爬 → 经 wayback 取 PDF）；另 NAS 上有 2025-05 档案件内 `HelpFiles/CBDB Users Guide.pdf` **160 页**（sha256 `3b703c8e…`）与独立件 `CBDB_Users_Guide_2018.pdf`（5,478,089 B）；
- **无任何入库/迁移章节**；且 2018 版文本层 134,716 字符中搜 `9999` → **0 命中**，`placeholder`/`sentinel`/`unknown` 亦 0 命中 → **官方连占位符约定都不解释**；`CHGIS_PT_ID` 这座桥官方 Guide **从未提及**；
- 社区亦无现成开源 CBDB→PG 管线（学术侧有 CBDB 关系库论文与 R/Python 访问包，皆非 PG 迁移）。
- **⇒ 含义**：没有官方文档可当保真基准；真值只能来自源件自身结构与字节（DBF 头、`.prj`、zip 成员表、sqlite schema、xlsx 首行）。官方 Guide 只可当**旁证**（读它了解字段语义），不可当**判据**。

### 14.2 平台方（PostgreSQL／PostGIS）：**有**，且已逐条对照

- **PG18 官方《Populating a Database》（文档 §14.4）九条** vs 旧方案：七条天然吻合（关 autocommit／用 COPY 不用 INSERT／先去索引灌完再建／**去 FK 约束**／增大 `maintenance_work_mem`／灌毕 ANALYZE／pg_dump 恢复要点）；一条原缺后补入（**`max_wal_size` 临时 4GB、毕即 RESET**）；一条有据不采纳（`wal_level=minimal` 须重启实例且废既有基础备份，收益仅 600MB 级）。
  - 其中第 4 条官方原话是 **"necessary, not just desirable"** → 与本方案"保真层不建 FK"**互相背书**（也解释了现库 FK＝0 系设计选择而非缺陷）。
- **PostGIS 3.6 手册第 4 章 §4.7 "Loading Spatial Data"**：官方内建装载法两条——① SQL（WKT/WKB 经 `psql -f`）② **`shp2pgsql`**，关键旗标 `-D`（dump 格式＝COPY 快速模式，官方原话 *"Use this for very large data sets"*）。

### 14.3 工具方（GDAL／ogr2ogr）：有行为文档，但**默认行为正是坑源**

LDID 猜编码（→ 820 表列双重编码，P-05）／`-append` 按列名映射丢列不报 warning（→ P-09）／`.xls`(BIFF) 在 GDAL 3.13.2 **无任何表头开选项**（实测 `HEADERS=FORCE` 无效 → P-10）／`SHAPE_ENCODING=GBK` 下孤立 `0xFC` 静默丢弃（→ P-07）。
**⇒ 含义**：方案中每一项都不得依赖 GDAL 默认值，必须在 `sources.yaml` 显式声明；凡工具无开选项可声明者，必须在 `verifier/` 侧用独立读法兜住。

### 14.4 大路工具之取舍

- **pgloader**（sqlite→PG 社区首推，Neon/Netbird/Render 三家迁移指南一致）：**本案不用**——装它＝32 宿主系统改动（超实例边界须另令），而本管线 python3 标准库零新装、且类型映射/BLOB 十六进制/NULL 语义全可控。
- 社区踩坑清单（类型亲和性、BLOB、标识符大小写、布尔表示）：本文 §5.3 映射表逐条已覆盖。
