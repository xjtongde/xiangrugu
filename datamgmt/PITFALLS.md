## 甲 验收类（最贵的四条：全部缺陷都从这里静默通过）

### P-01 验收基准取自被验收者自身
- **实证**：`chgis.v4_gns` 广西 **4,099 行漏装**（全 212 档案中唯一双重后缀件 `v4_gns_guangxi_gbk.zip.zip`），**recon 无一行留痕**，而验收结论写着"未解决终态为零，无一静默丢"——后被只读审计**证伪**（B-05；旧方案 §15.9（原件已删，`git show 75ecd77:docs/cbdb-load.md`））。另 `b2b2j.py:load_xls` 之 `ok=(fcn==pgc)`：GDAL 自数 Feature Count 对比库内行数，**表头行两边同计故恒等**（B-06）。`b2b3.py` K 腿 xlsx 段仅判 `pgc not in ('ERR','0')`——连数都不对。
- **病根**：期望值由装载器自己的枚举产生，**基准与被验收者是同一个东西**。
- **拦截点**：`import-plan.md` H-1、闸2（真值现算）、§6.1 独立性铁律第 2 条。
- **禁令**：**期望值不得由装载器产生**；一切真值须由 `load/truth/` 独立直读源件现算。

### P-02 行数与指纹相等 ≠ 值相等
- **实证**：`chgis.v4_gns.name` **2,287 行**＋`pref_py` **1 行**丢末尾变音符（`Hsü-t'uan`→`Hs-t'uan`、`Mo-li-hsü`→`Mo-li-hs`）。FIX10 验收查了"无杂字残留／行数相符／指纹不变／逐省行数 30/30 全等／`(ufi,uni)` 键完整性 0 缺"——**全过**，而值其实丢了字。直到用户追问"会不会张冠李戴"、**直读源 DBF 原始字节逐行比对**才暴露（B-11）。
- **病根**：以行数、指纹、键完整性代替值比对；**"无杂字"检查只证没有多出来的字，证不了没有少掉的字**。
- **拦截点**：闸3（值级，§6.3 四种比对法）、§7.1 解码单元测试。
- **禁令**：**任何表的合格证明必须来自值级比对**；行数与指纹只能当粗筛，不得写入结论。

### P-03 叙事账当合格证明
- **实证**：旧方案 §15（原件已删，`git show 75ecd77:docs/cbdb-load.md`） 以"验收八项全过"收口，其中**三项后被 §15.9 补正注证伪**（recon 行数、OK/REPAIRED/AS_IS 计数、总行数 8,580,012→8,584,097）。
- **病根**：验收结论是人写的散文，**无法机器复核**，也无法在数据变动后自动失效。
- **拦截点**：§6.5 合格证书（每表一份 JSON，机器可读、带时点与工具链版本）。
- **禁令**：**无证书的表＝未验收＝不合格**；证书之外不得另有"验收通过"的说法。

### P-04 局部观察被当全局结论（抽样不声明覆盖率）
- **实证**：FIX10 验收语"残余非 ASCII 仅 5 个合法变音字母"系局部观察，被当成"无字符丢失"的全局证明（B-11 补正注就地纠正）。
- **病根**：抽样结论未声明覆盖率与置信度。
- **拦截点**：§6.3 分级策略（覆盖率必须写入证书）。
- **禁令**：**"抽样通过"四字不得单独出现在任何验收结论里**，必须附覆盖率。

## 乙 编码类（第二批的最大事故源）

### P-05 让 GDAL 按 LDID 猜编码
- **实证**：第二批"编码大事件"——`enc=None` → GDAL 按 LDID 猜 latin1 → **820 个表列双重编码**，事后以 SQL 就地"无损修复" **2,483,167 行**＋三表重装（旧方案 §15，原件已删）。
- **病根**：未显式声明编码，把判定权交给工具的默认行为。
- **拦截点**：§5.4 列级解码判定表、§5.3 显式类型/编码。
- **禁令**：**任何文本列的编码必须显式声明并附依据**，禁止依赖工具默认。

### P-06 编码判定粒度错在"文件"而非"列"（同一 DBF 内混合编码）
- **实证**：`v5_gns_anhui_gbk.dbf` 之 `NAME`/`NM_ASCII`/`SORT_NAME`/`PREF_PY` 系**单字节 latin1/cp1252**（威妥玛拼音 `ü` 存作裸字节 `0xFC`；源字节 `48 73 FC 61 6E`＝`Hsüan`），而**同文件** `CNTY_CH` 系**真 GBK**（4,099 记录全含高位字节）。文件名带 `_gbk` 更具误导性（B-11 根因分析）。
- **病根**：按文件级 LDID 一刀切。
- **拦截点**：§5.4（逐列判定，每条带 `evidence`）。
- **禁令**：**编码判定粒度是"列"，不是"文件"**；文件名/后缀不得作为编码依据。

### P-07 `SHAPE_ENCODING=GBK` 下孤立高位字节被静默丢弃
- **实证**：FIX10 补装路径在 `--config SHAPE_ENCODING GBK` 下，字段末尾的孤立 `0xFC` **无后继字节可配** → GDAL **静默丢弃**（不报错、不告警），涉 **323/324 行**；guangxi 一件 360 记录含 `0xFC`，其中 **309 处落在字段末尾**（B-11）。
- **病根**：把单字节编码的字节流交给多字节解码器。
- **拦截点**：闸3 值级、§7.1 解码单元测试（`decode(encode(x))==x` 与全量可解断言）。
- **禁令**：**凡源件含孤立高位字节，必须直读字节自行解码，不得交给 GDAL**。

### P-08 用 SQL 逆变换"修"编码，反而丢字
- **实证**：FIX5 期以 `convert_from(convert_to(col,'LATIN1'),'UTF8')` 修中文列——而**孤立 `0xFC` 非合法 UTF-8 序列**，该变换于此**丢字 1,964 行**（B-11 原装路径）。
- **病根**：装错之后试图在库内"无损"修回，而变换本身不无损。
- **拦截点**：H-3（保真层永不 UPDATE）。
- **禁令**：**修编码只能在装载时修对**；装完再逆变换一律禁止。

## 丙 结构类

### P-09 `-append` 按列名映射，名不匹配即静默丢列
- **实证**：GNS 每省字段名带本省前缀（`AH_INT_ID`/`AH_EXT_ID` vs `GX_INT_ID`/`GX_EXT_ID`，安徽 32 字段、广西 31 字段且无 `LC`）；`load_gns()` 以首省 `-overwrite` 建表、余 29 省 `-append` → **29 省前缀 ID 列全部丢弃，GDAL 不报 warning、不建列**，账面无一行提及（B-10）。
- **病根**：PostgreSQL 驱动按名映射，而并表各成员字段名不同。
- **拦截点**：闸1（列集差集必须为空）。
- **禁令**：**并表装载必须先求各成员字段名并集，逐成员显式映射**；不得以首成员定表结构。

### P-10 xls/xlsx 表头被当数据、真列名尽失
- **实证**：八张 xls/xlsx 源表**表头行被当作数据装入**，产生 **114 个 `fieldN` 合成列**；FIX11 删 **14 行**（表头＋版权前言）后，三表仍留 **67 个 `fieldN` 伪列**（逐列实测非空计数皆为 0）（B-06／I-02）。且 `.xls`（BIFF）在 GDAL 3.13.2 **无任何表头开选项**（实测 `-oo HEADERS=FORCE` 无效）→ 一半无解；`.xlsx` 若真表头不在第 1 行（如 `china_pop` 前有 3 行版权前言），强加 `HEADERS=FORCE` 反把前言当列名。
- **病根**：把"结构识别"交给工具默认，而工具在此无开选项或开选项会误伤。
- **拦截点**：§5.2 腿 C（xls/xlsx **不经 GDAL**，直读单元格后 `\copy`）、H-4（删除须机器可复核依据）。
- **禁令**：**xls/xlsx 一律直读单元格后 COPY**；每一处删行必须附"该行文本＝＝列名集／位于数据起始行之前"的机器判据。

### P-11 成员枚举用锚定单后缀正则，双重后缀件被漏
- **实证**：`b2b3.py:182`／`b2fix2.py:96`／`b2fix4.py:48` 三处正则 `\.zip$`（或 `\.(zip|ZIP)$`）→ 漏掉 `v4_gns_guangxi_gbk.zip.zip`（P-01 的直接成因）；修法改 `(\.zip)+$` 并加 `re.I`（实测命中 **30 件**、**过度匹配 0 件**、与源侧 DBF 头合计逐位相符）。
- **病根**：对发布方的命名习惯作了过强假设。
- **拦截点**：§7.1 单元测试（以该件为回归用例）、`truth/zipmember.py`。
- **禁令**：**成员枚举不得用锚定单后缀正则**；枚举结果必须与源侧件数真值对账。

### P-12 工作台账以 append 追加且落 /tmp
- **实证**：`recon_b2a.tsv` **887 重复行**（五键去重后 883）、**4 个幻影 target**、诸文档计数**基准混用未声明**（B-08）；脚本工作目录 `W='/tmp/pg32b-load2'`、`REC=W+'/recon_b2a.tsv'`，以 `open(REC,'a')` 追加——该目录**2026-09-29 实测已不存在**，现存台账系事后抢救到 `ops/harvard/load-b2/` 的副本。
- **病根**：台账无唯一键、无落盘位置纪律。
- **拦截点**：§4.1（recon 落仓内、带唯一键 upsert）、P-16（资产入库）。
- **禁令**：**工作账不落 `/tmp`**；台账写入必须带唯一键（upsert，不 append）。

## 丁 空间与栅格类

### P-13 源件已声明的 CRS 被当成需要推断的问题
- **实证**：`usedata/harvard-full/…/M7WEFY/v5_gns_anhui_gbk.zip` 内 `.prj` **原文明写**：`PROJCS["Xian_1980_GK_Zone_19", … PROJECTION["Gauss_Kruger"], PARAMETER["False_Easting",19500000.0], PARAMETER["Central_Meridian",111.0], … UNIT["Meter",1.0]`。而我方 FIX6/FIX8 判"实为 **2327**"（**误判**），FIX9 又"空间库实证"改判 **2333**，执行 `b2fix9.py:15`：`ALTER TABLE chgis.v5_gns ALTER COLUMN geom TYPE geometry(Geometry,4326) USING ST_Transform(ST_SetSRID(ST_Transform(geom,2327),2333),4326)` → **两次投影变换就地改写 130,665 行几何，源件原值在库里已不存在**。库内实测 `ST_SRID(geom)=4326`、值为经纬度（`Lülin` 119.3333/30.9500）。`chgis.v4_gns.geom` 同为 4326/经纬度，**极可能同类，待验**（源件在外层 zip 内，本轮未解包）。**本条 2026-09-29 新查，尚未入 `bugs.md`。**
- **病根**：源件已声明的事实被当作待推断的问题；推断错过一次；每次推断都就地改值。
- **拦截点**：H-2、闸1（SRID ＝＝ `.prj` 声明）、§5.3（几何禁 `ST_Transform`）。
- **禁令**：**CRS 一律照 `.prj` 存**；投影变换属下游，在查询/视图里做，**永不落保真库**。源件未声明 `.prj` 者记 `srid: 0` 并登记，**不得推断**。

### P-14 就地 UPDATE 使"库内值＝源件值"判据永久失效
- **实证**：FIX5（编码逆变换 2,483,167 行）＋FIX9（几何两次变换 130,665 行）＋FIX10（补装 +4,099）＋FIX11（表头去污 −14）累积之后，现库**无法**用"逐值对源件"来证明正确，只能靠 §13/§15 叙事账（P-03）。
- **病根**：把"修"实现为"改已装好的值"，而不是"改装载方式后重装"。
- **拦截点**：H-3、§5.5（staging→过闸→原子换名，重跑即重装）。
- **禁令**：**保真层永不 `UPDATE`／`DELETE`**；发现我方错 → 重装该表。

### P-15 栅格装载参数未逐项记账
- **实证**：第二批以 `raster2pgsql` 装 29 表 DEM（含 `postgis_raster` 3.6.4 补装），账内记了"DEM 真高程 54m@历山书院与首批互证"这一**点验**，但**分块大小、像素类型、nodata、压缩**等参数未逐项入账 → 无法判断工具是否改写了像素表达。
- **病根**：以单点抽查代替参数级声明。
- **拦截点**：§5.3（参数入证书）、§6.3（栅格比对法与覆盖率声明）。
- **禁令**：**栅格装载参数必须逐项显式并写入合格证书**；点验不得代替参数声明。

## 戊 工程卫生类（决定"能不能重建"）

### P-16 可重建资产不入版本库、且无副本
- **实证**：`ops/` 在 `.gitignore:8` → **23 支 `b2*.py` 全不入 git**（`git ls-files` 内装载相关只有 `docs/cbdb-load.md`，该文档亦已于 2026-09-29 删除）；NAS 侧 `find /mnt/wd61workmetadata -name "b2*.py"` **实测无副本** → 重建能力**单点在本机磁盘**。
- **病根**："运维工作区不入仓"的旧例被套用到**唯一的重建资产**上。
- **拦截点**：§3 前置 P-3、§4.1（`load/` 入 git）。
- **禁令**：**一切可重建资产（清单、装载器、验证器、解码判定表、recon）必须入版本库**。

### P-17 路径腐化三层，无一指向权威源
- **实证**（2026-09-29 实测）：脚本内 **15 处**硬编码 `/mnt/nas-mirror/61/workmetadata/harvard-full/…`（该路径 2026-09-27 起**项目读写皆禁**）；**3 处**硬编码 `/mnt/wd61workmetadata/harvard-full/…`——该路径 09-28 搬入 `xiangrugudata/` 后**实测已不存在**（照原样重跑即失败）；**0 处**指向权威源 `/mnt/wd61workmetadata/usedata/`。
- **病根**：绝对路径散落在每支脚本里，数据区一改布局即全体失效。
- **拦截点**：§5.1（`key` 用相对键，双根共键规则见 `datamgmt/config/roots.yaml` 之 `path_resolution`）、单一根变量。
- **禁令**：**禁止硬编码绝对路径**；源根只在一个变量里，其余一律相对键拼接。

### P-18 无总控、FIX 链非幂等
- **实证**：23 支脚本各自为政（`b2a`/`b2a2`/`b2acc`/`b2acc2`/`b2b1`/`b2b2`/`b2b2j`/`b2b3`/`b2b3fix`/`b2b3fix2`/`b2chk`/`b2chk2`/`b2fix`/`b2fix2`…`b2fix9`/`b2post`/`resolve_src`），**无一支总控**；装载顺序只存在于 §13/§15 叙事账；多支 FIX 系针对**当时库态**写的一次性补丁，重放到空库不等价。
- **病根**：探索式推进的产物没有收敛成声明式配置。
- **拦截点**：§5.1（`sources.yaml` 一页读完）、§5.5（幂等流程）、§7.4（幂等断言：连跑两遍逐值相同）。
- **禁令**：**任何装载步骤必须能在空库上重跑得同一结果**；一次性补丁不得进入正式流程。

### P-19 无 dump 即谈删库
- **实证**：pg32b **无任何 `cbdb` 库 dump**（`codemap.md` §2 实例行明载"备份调度/落盘＝另派 agent"）；pg32b 与生产 `pg32` **共实例**（4 核/7G，另有 n8n/chainlit/graphrag 等在跑）；库现 **4,771MB／395 表／8,584,318 行**（`count(*)` 口径；账面 pg_stat 口径 8,584,097，差 221）。
- **病根**：把"能从源重装"当成"不需要备份"，而重装能力本身尚未验证（P-16/P-17/P-18）。
- **拦截点**：§3 前置 P-1、§7.4（彩排在别的实例上先跑）、§10 阶段四（dump→口令→删库）。
- **禁令**：**删库前必有 dump；删库须用户逐案口令**（R-01＋R-07）；正式窗口须带压力门禁。

## 己 判断与汇报类（本轮复核批新得，最容易被忽视）

### P-20 汇报时限定词丢失，局部结论扩成全局
